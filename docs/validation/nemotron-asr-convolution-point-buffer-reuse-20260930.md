# Nemotron ASR convolution point-buffer reuse — 30 September 2026

`Encoder0Convolution.forward` now places the depthwise result in the first half of its owned pointwise-1 buffer after GLU has consumed pointwise-1. GLU has independent storage and the result is used internally; this preserves public output ownership and cache commit order. The destination is cleared, although the depthwise loop writes every element. No numerical tolerance or GPU code changed.

Baseline: clean `c245faa3cf1ca1e56a606eb705d01c03b84be1e2`, Go 1.26.3, Linux amd64, i7-12700, `GOMAXPROCS=4`, released ASR checkpoint SHA-256 `9eebdd6590289cb3030f310858f3df93256600a800a3e8200c5993d5f967e174`. Three three-iteration 11-second JFK PCM benchmark samples after the change used **1,285,514,176 B/op and 23,124 allocs/op**, versus the previous three three-iteration samples at **1,299,276,736 B/op and 23,964 allocs/op**. This is about **13.76 MB and 840 fewer allocations per warm request**, in addition to prior [cached-attention](nemotron-asr-cached-attention-buffer-reuse-20260930.md) and [cached-block residual](nemotron-asr-cached-block-residual-reuse-20260930.md) passes. The after timing range was 6.53–6.81 seconds/request versus 6.47–6.68 seconds before. The ranges overlap; no latency improvement is accepted.

Pinned PyTorch convolution intermediates (pre-norm, pointwise-1, GLU, depthwise, depth norm, activation, output and residual) and cached-block chunks at lookaheads 0 and 3 had zero values outside existing thresholds. The 100-second JFK PCM generation reference passed with 1,663 decisions, 411 nonblank, zero decision mismatches and zero input/tower outliers. An AMI ES2004a 530–630-second CPU-only CLI process took 59.62 seconds including WAV/checkpoint load. Its transcript-only WER remained **88/274 = 0.321168** with unchanged edit counts; one request cannot establish a speedup.
