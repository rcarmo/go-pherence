# Nemotron ASR and diarisation: bounded CPU reference

Two user-approved NVIDIA checkpoints ran with a pinned Hugging Face Transformers CPU reference against the repository's 11-second mono JFK WAV. This establishes local loading and one-recording execution. It does not establish native Go inference, transcription accuracy, diarisation error rate, streaming-cache correctness or production readiness.

## Native offline frontend: scalar and checked SIMD slice

`loader/audio/NemotronLogMel` implements the shared offline centered 16 kHz/128-mel processor boundary in native Go. It applies 0.97 pre-emphasis, a symmetric 400-sample Hann window, 512-point real FFT, Slaney-normalised mel weights and natural log with the reference's `2^-24` guard. It returns owned frame-major `[floor(samples/160)+1,128]` features; the final STFT frame is masked to zero as in the pinned processor. This is **only** a feature frontend: neither RNNT transcription nor diarisation transformer/head runs in Go. This bounded API accepts 1–480,000 finite mono samples (up to 30 s); longer jobs require bounded chunk/stream state with independent seam tests.

`loader/audio/testdata/nemotron_jfk_transformers_5_18_features.f32.gz` contains the independent PyTorch/Transformers 5.18.dev0 CPU reference tensor for the pinned JFK input (1101×128 F32, 1100 valid frames). Regenerate it with `scripts/nemotron_feature_fixture.py` and the pinned local ASR processor. The input SHA-256 above checks provenance, **not** equality of generated features. Tests compare every value by absolute/relative tolerance `5e-4 + 1e-5*abs(reference)` and mean absolute error ≤`1e-5`. On the JFK fixture, both the Go scalar mel path and checked AVX2/FMA projection stayed inside all tolerances: maximum absolute error `3.66211e-4`, mean absolute error about `1.14e-6`. The tolerance accounts for F32 FFT/magnitude rounding, reduction order and low-energy log amplification; no tolerance was widened to accept the SIMD path. The scalar path is a dispatch reference, while the PyTorch fixture is the independent numerical reference. Tests cover short/tail lengths, invalid/non-finite input, caller preservation, retained output and FFT scratch bounds/overlap. With `GODEBUG=cpu.all=off`, checked dispatch fell back to scalar and repeated reference tests passed. The source has no Go-RVV frontend evidence, and cross-builds are compile-only.

On the local Intel i7-12700, Go 1.26.3/Linux amd64 at `GOMAXPROCS=1`, five same-CPU warm 11-second frontend samples (30 iterations each) placed scalar mel projection at 37.65–40.14 ms/op and checked AVX2/FMA mel projection at 7.57–8.11 ms/op. These are full **frontend** calls, including window/FFT/log, excluding WAV I/O and model inference. The checked projection is about 4.6–5.3× faster for this input; separate host activity was not controlled enough to call this a model speedup. Reusing caller-owned FFT work buffers and lazy immutable filter weights reduced warm allocation from 14,093,312 B / 3,304 objects to 2,408,448 B / 3 objects per call. These bytes include the owned output and per-call pre-emphasis/power storage. A normal-rate CPU profile attributes about 59% of sampled flat time to pure-Go `fft.ForwardRealInto`, the next measured hotspot. Native ARM64, sustained concurrency and in-kernel latency have not been measured.

Evidence: `/workspace/tmp/nemotron-feature-fixture.log`, `/workspace/tmp/nemotron-jfk-frontend-bench-{first,reuse,final}.log`, `/workspace/tmp/nemotron-jfk-frontend-scalar-matched.log` and `/workspace/tmp/nemotron-jfk-simd-cpu.pprof` (local, not committed). Run reproducible package tests with `GO_PHERENCE_DISABLE_NVIDIA=1 go test ./backends/simd/fft ./loader/audio -run 'Test(ForwardRealIntoScratchAndBounds|NemotronLogMel)' -count=10`.

## Vulkan F32 mel projection: native RTX 3060 probe

The existing `VkLinearF32` shader was exercised as a 1100×257 by 128×257 mel-energy projection on the RTX 3060. An opt-in native test stages independently generated PyTorch STFT power rows and librosa mel weights from `scripts/nemotron_vulkan_projection_fixture.py` into a bounded host-visible Vulkan arena. It checks the result against a float64 projection from the same pinned reference inputs and against checked CPU SIMD, rejects a software Vulkan device, checks resource release, and records upload, dispatch and download separately. The fixture files stay under `/workspace/tmp/nemotron-vulkan-projection/`; no GPU processing entered the default frontend.

Three isolated `GO_PHERENCE_TEST_NEMOTRON_VULKAN=1` runs passed on NVIDIA GeForce RTX 3060. Maximum absolute error against the float64 projection was `8.04e-7`, mean absolute error `6.73e-10`, and maximum difference from CPU SIMD `9.54e-7`; the test budget is `2e-3 + 2e-4*abs(reference)` with mean ≤`1e-4`. This conservative budget covers F32 reduction drift at low-energy rows, with the measured distribution far below it; it does not establish generated-transcript equivalence. Across the three runs, first upload of power/weights/zero bias took 0.141–0.201 ms; first dispatch 0.354–0.587 ms; first download 0.024–0.188 ms. Five resident dispatches per run ranged 0.241–0.455 ms. Five CPU SIMD projections from the same power and weights ranged 1.94–3.89 ms, while one complete CPU SIMD frontend call per run was 7.60–9.56 ms. These diagnostic timings have different scopes and do not establish a whole-frontend GPU win: the FFT and frontend input preparation still run on CPU, and initial model/kernel/arena setup was excluded. A device-resident full frontend and repeated end-to-end request cost remain unmeasured. No Vulkan path was made the default.

Reproduce with `GO_PHERENCE_TEST_NEMOTRON_VULKAN=1 GO_PHERENCE_VULKAN_DEVICE='NVIDIA GeForce RTX 3060' GO_PHERENCE_NEMOTRON_VULKAN_FIXTURE_DIR=/workspace/tmp/nemotron-vulkan-projection GO_PHERENCE_DISABLE_NVIDIA=1 go test ./backends/vulkan -run '^TestNemotronVulkanNativeMelProjection$' -count=3 -timeout=2m -v`. Regenerate inputs with the pinned CPU environment and `scripts/nemotron_vulkan_projection_fixture.py --out /workspace/tmp/nemotron-vulkan-projection`. Raw evidence is in `/workspace/tmp/nemotron-vulkan-projection-native-3.log` (not committed).

## PTX/CUDA F32 mel projection: native RTX 3060 probe

The existing `backends/nvidia/runtime.Sgemm` PTX path was exercised on the **same** PyTorch-generated power and mel-filter inputs as Vulkan. CUDA SGEMM expects row-major `B[K,N]`, so this probe transposes the 128×257 filter matrix to 257×128 on the CPU before upload; that cost is reported separately. An opt-in device test compares the output against float64 projection and checked CPU SIMD using the same `2e-3 + 2e-4*abs(reference)` per-value and `1e-4` mean-error budgets, checks finite resident output, and synchronises every timed dispatch. The default runtime variant is its existing oracle PTX kernel; this experiment adds no model code, default dispatch or PTX shader.

Three isolated native RTX 3060 runs passed. Maximum absolute difference from float64 reference was `8.04e-7`, mean absolute difference `6.73e-10`, and maximum difference from CPU SIMD `9.54e-7`. Across these runs, transpose took 0.039–0.058 ms, upload 0.116–0.182 ms, first dispatch plus synchronisation 0.131–0.148 ms, and first download 0.092–0.098 ms. Five resident dispatch-and-sync samples per run took 0.122–0.176 ms. Matched checked CPU SIMD projection samples ranged 1.93–2.43 ms. These are diagnostic operator timings, not a controlled full-frontend or model benchmark. CUDA initialisation, PTX module load, allocation, CPU FFT/power extraction, log/mask, audio I/O and complete model execution are excluded. Warm device reuse may help once an entire graph is resident; no such graph exists for these models here.

Reproduce with `GO_PHERENCE_TEST_NEMOTRON_PTX=1 GO_PHERENCE_NEMOTRON_PTX_FIXTURE_DIR=/workspace/tmp/nemotron-vulkan-projection go test ./backends/nvidia/runtime -run '^TestNemotronPTXNativeMelProjection$' -count=3 -timeout=2m -v`. The input generator and pinned CPU environment are the same as for Vulkan. Raw local evidence: `/workspace/tmp/nemotron-ptx-projection-native-3.log` (not committed). The GPU frontend and full ASR/diarisation execution have not been qualified; keep the CPU SIMD frontend as the default.

## Diarisation input stack projection: released-weight boundary

The pinned diarisation checkpoint's `model.audio_tower.embedder.projection.weight` is a bias-free F32 `[512,1024]` tensor. Transformers groups eight adjacent 128-mel frames, zero-pads the last incomplete group and projects `[ceil(frames/8),1024]` into 512-wide audio embeddings. `model/nemotrondiarization/StackingProjection` loads and owns that weight, checks finite values and frame bounds, and runs scalar or checked SIMD `DenseNTTo`. It does not execute the 31-layer audio transformer or eight-speaker head. An opt-in released test verifies the checkpoint's size and SHA-256 before loading it, then closes the mapped file while retaining the owned weight.

`scripts/nemotron_diarization_stacking_fixture.py` independently generated the pinned PyTorch `[1101,128]` feature and `[138,512]` projected-output fixtures from `testdata/jfk.wav`. Both source features and projected values are kept as compressed F32 fixtures under `model/nemotrondiarization/testdata/`; their input provenance is tied to the JFK WAV SHA-256 above. With **independent reference features**, scalar max/mean absolute error was `2.175e-4`/`6.13e-6`, checked SIMD `1.178e-4`/`4.31e-6`. With Go frontend features composed into the same projection, scalar max/mean was `2.213e-4`/`1.05e-5`, SIMD `1.879e-4`/`9.20e-6`. No values exceeded `2e-3 + 2e-4*abs(reference)` and mean ≤`1e-4`. The budget covers F32 projection reduction order and accumulated frontend rounding; the observed distribution is considerably narrower. Tiny tests cover 1/7/8/9/15/16/17-frame tails, zero padding, non-finite/malformed input, caller preservation and returned-output retention. With `GODEBUG=cpu.all=off`, the checked path falls back to scalar and passes repeated released parity. This does not validate frame-to-speaker timestamps or generated diarisation quality.

On the i7-12700, Go 1.26.3/Linux amd64, `GOMAXPROCS=1`, five warm 138-row projection samples (30 iterations each) placed scalar at 37.65–39.05 ms/op and checked AVX2/FMA at 2.46–2.69 ms/op, both allocating 851,968 B in two objects for owned stacking input/output. Checkpoint loading, frontend computation and speaker head are excluded. These samples support a local operator speedup, not a whole-model speedup.

An opt-in native `VkLinearF32` projection probe on RTX 3060 passed three runs against the PyTorch `[138,512]` fixture, maximum absolute error `2.194e-4`, mean `5.92e-6` and CPU SIMD maximum difference `2.289e-4`. First upload, dispatch and download totalled 0.93–1.31 ms; resident dispatch ranged 0.442–0.527 ms; matched CPU SIMD projection samples took 2.18–2.84 ms. The same input and released weights passed three native PTX SGEMM runs with the same output error. PTX required a CPU transpose from `[512,1024]` to `[1024,512]` taking 1.71–1.89 ms, plus first upload/dispatch/download of 0.52–0.65 ms; resident dispatch-and-sync ranged 0.248–0.295 ms. PTX therefore has no established transfer-inclusive benefit without persistent prepared weights. All GPU timings exclude model load, kernel/arena/device initialisation and full frontend/transformer work. Neither GPU path is the default.

Regenerate fixtures with `scripts/nemotron_diarization_stacking_fixture.py --out /workspace/tmp/nemotron-stacking` and GPU input tensors with `scripts/nemotron_stacking_device_fixture.py --out /workspace/tmp/nemotron-stacking-device` using the pinned CPU environment. Opt-in tests are `TestReleasedStackingPyTorchParity` (`GO_PHERENCE_NEMOTRON_DIARIZATION_MODEL=.../model.safetensors`), `TestNemotronVulkanNativeDiarizationStacking` and `TestNemotronPTXNativeDiarizationStacking` (each uses `GO_PHERENCE_NEMOTRON_STACKING_FIXTURE_DIR=/workspace/tmp/nemotron-stacking-device` and a native opt-in flag). Raw evidence is in `/workspace/tmp/nemotron-stacking-{parity-composed,onecpu-five,vulkan-native-3,ptx-native-3}.log` (not committed).

## ASR causal Conv2D stem: released first-operator boundary

The 0.6B ASR encoder starts with a causal 3×3 F32 Conv2D, stride 2 in time and frequency, mapping 1 channel to 256. Its offline padding is `(2,1)` on both axes, yielding channel-major `[256, floor(frames/2)+1, 65]` pre-activation values for `[frames,128]` input. `model/nemotronasr/StemConv2D` implements **this first stem only**, with scalar and checked SIMD GEMM paths. It does not include ReLU, valid-frame masks, the two depthwise/pointwise stages, linear projection, 24-layer encoder, RNNT predictor/joiner or streaming caches. The opt-in loader verifies the pinned 2,552,062,944-byte ASR safetensors SHA-256 before copying the `[256,1,3,3]` weight and 256-element bias.

`scripts/nemotron_asr_stem_fixture.py` independently generated bounded PyTorch/Transformers CPU features, released stem weight/bias and pre-activation output for the first 32 JFK feature frames. The expected tensor is `[256,17,65]`, saved as compressed F32 under `model/nemotronasr/testdata/`. Tiny scalar and checked SIMD comparisons use `3e-5 + 2e-5*abs(reference)` per value and mean absolute error ≤`3e-6`, with no values outside tolerance. Scalar max/mean error was `1.907e-5`/`4.85e-7`; SIMD max/mean was `1.526e-5`/`5.29e-7`. Short and odd-length tail tests, malformed/non-finite rejection, caller preservation, returned-output ownership and repeated warmed scratch reuse pass. With `GODEBUG=cpu.all=off`, the SIMD entry falls back to scalar and passes the pinned fixture.

Five warm i7-12700/Go 1.26.3 `GOMAXPROCS=1` samples (30 iterations each) place the tiny scalar stem at 3.16–3.74 ms/op and checked SIMD at 0.67–0.82 ms/op. The SIMD implementation builds 3×3 patches and writes its matrix result **directly into owned channel-major output**, avoiding an extra full output tensor and transpose. Without supplied scratch it allocates 1,179,648 B in two objects per call; a warmed session-local `StemScratch` reuses the 40,960-byte patch buffer and allocates only the owned 1,138,688-byte output (one object), with 0.67–0.74 ms/op across five samples. The scalar path allocates the same owned output and takes 3.16–3.74 ms/op. A normal-rate CPU profile of the pre-direct-output SIMD slice put about 62.5% of sampled flat CPU time in checked `SgemmNT`, so further kernel changes need separate reference and whole-request evidence. This is a 32-frame operator benchmark; it does not measure a full ASR request or the remaining subsampling stages.

Reproduce with `GO_PHERENCE_DISABLE_NVIDIA=1 go test ./model/nemotronasr -run '^Test(StemConv2D|StemScratchReuse)' -count=10` and opt-in `GO_PHERENCE_NEMOTRON_ASR_MODEL=checkpoints/nemotron/asr/model.safetensors go test ./model/nemotronasr -run '^TestReleasedStemConv2DLoad$'`. Regenerate fixtures with `scripts/nemotron_asr_stem_fixture.py --out /workspace/tmp/nemotron-asr-stem` in the pinned CPU environment. Raw local evidence: `/workspace/tmp/nemotron-asr-stem-{released,direct-tests,direct-five}.log` (not committed).

## ASR first-stem projection: bounded Vulkan and PTX probes

The released first-stem 3×3 causal convolution uses time/frequency padding `(2,1)`, stride 2 and a bias. The existing Vulkan CHW Conv2D accepts only symmetric padding `kernel/2` and a bias-free result; the existing NVIDIA Ideogram Conv2D is stride 1 with same padding. Neither is a drop-in Nemotron causal stem. For a bounded operator comparison, `scripts/nemotron_asr_stem_device_fixture.py` exports the pinned PyTorch features as 1,105 3×3 patches plus released `[256,9]` weights and bias. The existing Vulkan `VkLinearF32` projects patches and includes bias; the existing PTX SGEMM projects patches after a `[256,9]`→`[9,256]` weight transpose and adds bias during the output reorder. Both tests compare with the PyTorch `[256,17,65]` fixture and a separate float64 patch×weight+bias calculation. They do not implement causal padding, feature extraction or the rest of the ASR model on GPU.

Three native RTX 3060 runs per backend passed `3e-5 + 2e-5*abs(reference)` per value and mean absolute error ≤`3e-6`. Against float64 accumulation, both measured maximum absolute error `2.053e-5` and mean `4.16e-7`. The F32 device outputs happened to match the PyTorch fixture exactly in these runs; that observation is diagnostic, **not** a generated-signal acceptance gate. The tests also reject non-finite results. Across the three Vulkan runs, first upload took 9–11 µs, first dispatch 294–785 µs, download 130–728 µs and channel-major reorder 270–687 µs; five resident dispatches per run ranged 181–421 µs. Across the three PTX runs, weight transpose took 2–8 µs, upload 25–32 µs, first dispatch plus sync 29–45 µs, download 242–483 µs and reorder/bias 491–610 µs; five resident dispatch-and-sync samples per run ranged 21–39 µs. These samples are diagnostic and have overlapping host activity. Their scopes exclude CPU patch extraction, kernel/device initialisation and remaining model stages. PTX's resident kernel is quicker for this small matrix, but the required download/reorder and CPU feature/patch work leave a full ASR request unqualified. CPU SIMD stays the only native frontend/stem path.

Run the opt-in probes with `GO_PHERENCE_NEMOTRON_STEM_FIXTURE_DIR=/workspace/tmp/nemotron-asr-stem-device`, `-timeout=2m`, and respectively `GO_PHERENCE_TEST_NEMOTRON_VULKAN_STEM=1` or `GO_PHERENCE_TEST_NEMOTRON_PTX_STEM=1`. Regenerate patch inputs with `scripts/nemotron_asr_stem_device_fixture.py --out /workspace/tmp/nemotron-asr-stem-device`. Raw logs: `/workspace/tmp/nemotron-asr-stem-{vulkan,ptx}-independent-3.log` (not committed).

## Diarisation first-layer Q/K/V: bounded Vulkan and PTX probes

The released first audio-transformer layer applies `LayerNorm(512)` before bias-free Q/K/V projections. The 16-row CPU SIMD path at `model/nemotrondiarization/Layer0QKV` passed independent PyTorch normalised-input and pre-RoPE Q/K/V fixtures. `scripts/nemotron_diarization_qkv_device_fixture.py` exports that same normalised input `[16,512]` and a released combined `[1536,512]` Q/K/V weight. The opt-in Vulkan `VkLinearF32` and PTX/CUDA SGEMM probes compare output with each independent reference, then with CPU SIMD. Normalisation, RoPE, attention, residuals, cache and speaker head do not run on the GPU here.

On an RTX 3060, three runs per backend had maximum absolute error `7.63e-6`, mean absolute error `2.38e-7`, zero values outside `3e-4 + 2e-5*abs(reference)`, and maximum CPU/GPU drift `6.68e-6`. Across the three Vulkan runs, upload took 381–480 µs, first dispatch 492–781 µs, download 6–36 µs, and fifteen resident dispatches 341–375 µs. PTX's host weight transpose took 1.60–2.70 ms, upload 158–299 µs, first dispatch plus sync 102–114 µs, download 24–53 µs, and fifteen resident dispatch-and-sync samples 53–61 µs. The weight transpose is a preparation cost, while the upload includes the normalised input and weights. Timings are isolated samples, not full-request latency. CPU SIMD GEMM samples spanned 343–505 µs in the Vulkan runs and 352–440 µs in the PTX runs; the whole CPU layer-normalisation/QKV operation is separately measured at 410–485 µs per 16 rows. No GPU default or full-model throughput claim follows.

Reproduce with `scripts/nemotron_diarization_qkv_device_fixture.py --out /workspace/tmp/nemotron-qkv-device`, `GO_PHERENCE_NEMOTRON_QKV_FIXTURE_DIR=/workspace/tmp/nemotron-qkv-device`, `-timeout=2m`, and respectively `GO_PHERENCE_TEST_NEMOTRON_VULKAN_QKV=1` or `GO_PHERENCE_TEST_NEMOTRON_PTX_QKV=1`. The generated raw F32 inputs are outside Git; the independent compressed Q/K/V references are in `model/nemotrondiarization/testdata/`.
