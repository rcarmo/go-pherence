# Pocket TTS native ARM64 preset-voice check

The released preset-voice Pocket TTS path passes correctness and zero-warm-allocation checks on a CIX P1 ARM64 board, but its measured generation is slower than real time there. This run did not test raw-audio voice cloning, training or native RVV.

The board ran Linux/ARM64 with `GOMAXPROCS=2`, `nice -n 10` and NVIDIA disabled. The test binary was built from go-pherence `f0259ae1` with Go 1.26.2 and `CGO_ENABLED=0`; binary SHA-256 was `7686e3ac503105eeb82e8a73e18bddf5681410bdb144f44837554da6efb018e0`. The imported preset-only English model, tokenizer and Alba voice assets matched the pinned SHA-256 values in `model/pockettts/released_assets_test.go`: `916ccd26…52344f`, `f498428e…d8c6687` and `69c32db6…1d8845`. No model assets entered Git. The first test attempt lacked the package's relative `testdata/` files; it failed before inference and was rerun after transferring a SHA-checked fixture bundle.

The selected released checks passed: FlowLM prefill (reported max absolute difference 2.7194619178771973e-6, EOS difference 6.67572021484375e-6), one-frame end-to-end generation, one-frame Mimi parity, batch versus frame streaming, tokenizer parity, tensor inventory and ten warm five-frame calls with zero heap allocations.

Three fresh-process benchmark runs per case, five warm calls per process, reported:

| Frames | Audio duration | Median ARM64 time | Range | Heap per call |
|---:|---:|---:|---:|---:|
| 1 | 80 ms | 502,182,248 ns | 502,129,729–529,766,794 ns | 0 B, 0 allocs |
| 5 | 400 ms | 1,861,029,346 ns | 1,792,832,368–1,873,433,705 ns | 0 B, 0 allocs |
| 25-frame capacity | Up to 2 s; deterministic run emits 1.2 s before EOS | 5,072,630,502 ns | 5,070,200,702–5,081,036,158 ns | 0 B, 0 allocs |

These are board measurements under its current workloads. The prior i7-12700 [inference record](pocket-tts-native-inference-2026-09-22.md) reported 51–54 ms, 143–147 ms and 398–427 ms for the same frame counts with different hardware and worker settings. The 25-frame-capacity run emits 15 frames before EOS, or 1.2 s of audio. Its ARM64 median is about 4.23 times the emitted audio duration; it does not pass a real-time target. Pinned outputs and allocation results establish a bounded native correctness path, not latency or production readiness.

A separate three-call ARM64 CPU profile measured 5,239,560,859 ns/op and sampled 16.19 CPU seconds, including setup. `FMA32Scalar` was 7.57 seconds flat (46.76%), `BF16DotF32` 2.99 seconds flat (18.47%) and `fmaMatrixScalar` 2.00 seconds flat (12.35%). `MimiDecoderCPU.DecodeFrameInto` was 11.54 seconds cumulative (71.28%), with `CausalConv1D.ForwardInto` at 10.16 seconds cumulative (62.75%). Percentages are CPU-sample shares, not wall-time shares. For causal convolutions with widths up to 256, `FMAMatrixF32Checked` selects `fmaMatrixScalar` on ARM64 to preserve the specified ascending-K F32 FMA order; BF16 x4 dot uses a scalar fallback outside amd64. A faster kernel needs numerical and released-waveform parity before selection. No kernel or default was changed in this measurement.

An opt-in ARM64 single-pass NEON matrix kernel now replaces the scalar FMA matrix step while preserving serial-K accumulation. It writes each output tile once without a preceding destination-clear pass. The existing matrix exact-order/bounds tests, eight normal-input shape comparisons with scalar results, signed-zero/subnormal/overflow/cancellation probes, and released FlowLM/Mimi/one-frame gates passed. A historical 25-frame output-hash test also matched across the original ARM64 scalar path and the NEON candidate; it has since been replaced by a numerical PCM comparison because generated signals must not be hash-gated. The previous amd64 output differed from ARM64; the cause of that cross-architecture difference was not isolated here. No tolerance was widened. Warm output still allocates 0 B and 0 objects.

Three rotated fresh-process comparisons (five warm calls per case) on the same board measured median 25-frame time 5,081,778,555 ns scalar versus 1,984,416,305 ns single-pass NEON (about 2.56 times faster). The 80 ms first-chunk medians were 504,931,629 versus 295,816,696 ns; five-frame medians were 1,793,952,394 versus 784,249,969 ns. A two-pass clear-then-SGEMM trial produced overlapping medians near 1.996 s and 1.978 s for the 25-frame case; the single-pass kernel avoids that redundant clear by construction, but the timing difference between the two NEON trials is not established. A three-call final NEON CPU profile sampled 6.53 CPU seconds: `BF16DotF32` 2.91 seconds flat (44.56%) is now the largest hotspot; `CausalConv1D.ForwardInto` fell to 0.57 seconds cumulative (8.73%). Percentages are CPU-sample shares, not wall-time shares. The 25-frame-capacity run emits 1.2 s of audio before EOS and takes about 1.98 s on this board; it does not meet real time for this measured case. A shared-activation four-row BF16 dot trial passed the existing tolerance-based x4 tests and the one-frame released gate, but differed by five float32 ULPs on one row at seven columns. It used separate `FMULS`/`FADDS` in place of the scalar reference's fused `FMADDS`; both paths decode the *same BF16 weights* and use the same F32 activations, so BF16 input quantization cancels in this comparison. For normalized BF16 weights, rounding to nearest has a relative bound near 2⁻⁸ (0.39%); the difference here is instead F32 operation rounding (unit roundoff 2⁻²⁴, about 5.96×10⁻⁸ per operation), compounded by accumulation and subsequent generation. The trial was reverted pending waveform assessment; the bitwise test remains a diagnostic for the exact-order kernel, not a general generated-audio acceptance gate.

The scalar BF16 reference compiles to `FMADDS`, so the second four-row candidate used fused multiply-add for every row while sharing one F32 activation load per column. The strict native bitwise test passes across 11 column widths and 16 seeded matrices per width; released FlowLM/Mimi/one-frame tests and the zero-warm-allocation gate pass. A 25-frame numerical comparison against the separately captured unchanged ARM baseline reports zero affected samples and zero measured error for this candidate. Bitwise kernel parity and matching PCM bytes are observations, not generated-signal hash acceptance gates. Three rotated fresh-process runs (five 25-frame calls each) on the same CIX P1 measured median 1,982,356,342 ns on the previous NEON FMA build versus 1,548,844,666 ns with fused BF16 x4, about 1.28× faster for that workload. First-chunk medians were 314,349,987 versus 222,825,996 ns; five-frame medians 754,998,520 versus 572,237,663 ns. Both paths reported 0 B and 0 allocations per warm call. A three-call fused-BF16 profile sampled 5.12 CPU seconds: `bf16DotF32x4Arm64Asm` was 2.32 seconds flat (45.31%); its share rose even while wall time fell. This remains native ARM64 evidence for the pinned preset voice, not a broader quality or sustained-load claim. The full native SIMD package also triggered an SGEMM parity test that fails identically on the pre-BF16 binary; two source-boundary tests require the repository tree absent from the transfer bundle. Focused BF16/GEMV/FMA native checks passed five repeats. A bounded shared-model concurrency check then used two request-owned sessions, five frames each, with distinct fixed noise streams and three simultaneous generations per test run. Five native CIX P1 test processes passed: each worker emitted 9,600 samples and had zero measured max/RMS drift against its separately run serial counterpart. This checks cross-talk and reset/reuse for these two workers; a native race-instrumented test was not run because the amd64 host lacks an ARM64 C toolchain/sysroot, and the ordinary native binary does not detect Go races. The host package race run passed, but skipped the opt-in released test without model files. Longer runs, more workers, cancellation and measured concurrent throughput remain open; sustained-load and production admission remain separate.

A later comparison recovered the original ARM baseline PCM from its saved diagnostic binary and verified its 192,000-byte payload against the diagnostic's logged output identity; the saved non-fused trial PCM is also 192,000 bytes. Hashes here serve *historical artifact identification only*, never waveform acceptance. On the CIX P1 deterministic 25-frame-*capacity* run, EOS stops generation after 15 frames (28,800 F32 samples at 24 kHz, 1.2 s). The 48,000-sample caller buffer has 19,200 unwritten zeros. Of the emitted samples, 28,711 differ. The emitted baseline peak is 0.333923668 and RMS is 0.057865876. Absolute error max is 3.13036144×10⁻⁵ (sample 15,290; 9.37448×10⁻⁵ of peak), emitted-sample RMS is 1.73419166×10⁻⁶ (2.99692×10⁻⁵ of signal RMS, 90.47 dB SNR). Absolute-error percentiles over the full 48,000-sample buffer, including the zero tail: p50 4.19×10⁻⁹, p95 1.79×10⁻⁶, p99 6.19×10⁻⁶, p99.9 1.63×10⁻⁵; 173 exceed 1×10⁻⁵ and two exceed 3×10⁻⁵. The same-host released parity test now reads a separately captured raw little-endian F32 baseline from `GO_PHERENCE_POCKETTTS_REFERENCE_PCM`, checks finite values and exact sample count, and reports absolute/RMS/peak-relative drift instead of a PCM SHA gate. Provisional measured-error ceilings of max 4×10⁻⁵ and relative RMS 5×10⁻⁵ leave modest headroom above the trial, not a claim of broader speech quality or an automatic change to the existing independent one-frame 3×10⁻⁵ oracle. Both the fused candidate against baseline (zero drift) and a baseline-versus-saved-trial diagnostic comparison (measured drift above) pass the new numerical gate. Converted 16-bit WAVs and a stereo A/B file (baseline left, trial right) were prepared from the full 48,000-sample buffer, so they include 0.8 s of silence after the 1.2 s utterance. Listening assessment and broader utterance/voice quality are **open**, so the non-fused trial remains unqualified. Reference provenance, model/voice/seed/architecture, and native logs must accompany each invocation; absent reference PCM skips rather than passes this opt-in gate.
