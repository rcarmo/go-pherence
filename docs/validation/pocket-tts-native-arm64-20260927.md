# Pocket TTS native ARM64 preset-voice check

The released preset-voice Pocket TTS path passes correctness and zero-warm-allocation checks on a CIX P1 ARM64 board, but its measured generation is slower than real time there. This run did not test raw-audio voice cloning, training or native RVV.

The board ran Linux/ARM64 with `GOMAXPROCS=2`, `nice -n 10` and NVIDIA disabled. The test binary was built from go-pherence `f0259ae1` with Go 1.26.2 and `CGO_ENABLED=0`; binary SHA-256 was `7686e3ac503105eeb82e8a73e18bddf5681410bdb144f44837554da6efb018e0`. The imported preset-only English model, tokenizer and Alba voice assets matched the pinned SHA-256 values in `model/pockettts/released_assets_test.go`: `916ccd26…52344f`, `f498428e…d8c6687` and `69c32db6…1d8845`. No model assets entered Git. The first test attempt lacked the package's relative `testdata/` files; it failed before inference and was rerun after transferring a SHA-checked fixture bundle.

The selected released checks passed: FlowLM prefill (reported max absolute difference 2.7194619178771973e-6, EOS difference 6.67572021484375e-6), one-frame end-to-end generation, one-frame Mimi parity, batch versus frame streaming, tokenizer parity, tensor inventory and ten warm five-frame calls with zero heap allocations.

Three fresh-process benchmark runs per case, five warm calls per process, reported:

These are board measurements under its current workloads. The prior i7-12700 [inference record](pocket-tts-native-inference-2026-09-22.md) reported 51–54 ms, 143–147 ms and 398–427 ms for the same frame counts with different hardware and worker settings. The 25-frame-capacity run emits 15 frames before EOS, or 1.2 s of audio. Its ARM64 median is about 4.23 times the emitted audio duration; it does not pass a real-time target. Pinned outputs and allocation results establish a bounded native correctness path, not latency or production readiness.

A separate three-call ARM64 CPU profile measured 5,239,560,859 ns/op and sampled 16.19 CPU seconds, including setup. `FMA32Scalar` was 7.57 seconds flat (46.76%), `BF16DotF32` 2.99 seconds flat (18.47%) and `fmaMatrixScalar` 2.00 seconds flat (12.35%). `MimiDecoderCPU.DecodeFrameInto` was 11.54 seconds cumulative (71.28%), with `CausalConv1D.ForwardInto` at 10.16 seconds cumulative (62.75%). Percentages are CPU-sample shares, not wall-time shares. For causal convolutions with widths up to 256, `FMAMatrixF32Checked` selects `fmaMatrixScalar` on ARM64 to preserve the specified ascending-K F32 FMA order; BF16 x4 dot uses a scalar fallback outside amd64. A faster kernel needs numerical and released-waveform parity before selection. No kernel or default was changed in this measurement.

An opt-in ARM64 single-pass NEON matrix kernel now replaces the scalar FMA matrix step while preserving serial-K accumulation. It writes each output tile once without a preceding destination-clear pass. The existing matrix exact-order/bounds tests, eight normal-input shape comparisons with scalar results, signed-zero/subnormal/overflow/cancellation probes, and released FlowLM/Mimi/one-frame gates passed. A historical 25-frame output-hash test also matched across the original ARM64 scalar path and the NEON candidate; it has since been replaced by a numerical PCM comparison because generated signals must not be hash-gated. The previous amd64 output differed from ARM64; the cause of that cross-architecture difference was not isolated here. No tolerance was widened. Warm output still allocates 0 B and 0 objects.

Three rotated fresh-process comparisons (five warm calls per case) on the same board measured median 25-frame time 5,081,778,555 ns scalar versus 1,984,416,305 ns single-pass NEON (about 2.56 times faster). The 80 ms first-chunk medians were 504,931,629 versus 295,816,696 ns; five-frame medians were 1,793,952,394 versus 784,249,969 ns. A two-pass clear-then-SGEMM trial produced overlapping medians near 1.996 s and 1.978 s for the 25-frame case; the single-pass kernel avoids that redundant clear by construction, but the timing difference between the two NEON trials is not established. A three-call final NEON CPU profile sampled 6.53 CPU seconds: `BF16DotF32` 2.91 seconds flat (44.56%) is now the largest hotspot; `CausalConv1D.ForwardInto` fell to 0.57 seconds cumulative (8.73%). Percentages are CPU-sample shares, not wall-time shares. The 25-frame-capacity run emits 1.2 s of audio before EOS and takes about 1.98 s on this board; it does not meet real time for this measured case. A shared-activation four-row BF16 dot trial passed the existing tolerance-based x4 tests and the one-frame released gate, but differed by five float32 ULPs on one row at seven columns. It used separate `FMULS`/`FADDS` in place of the scalar reference's fused `FMADDS`; both paths decode the *same BF16 weights* and use the same F32 activations, so BF16 input quantization cancels in this comparison. For normalized BF16 weights, rounding to nearest has a relative bound near 2⁻⁸ (0.39%); the difference here is instead F32 operation rounding (unit roundoff 2⁻²⁴, about 5.96×10⁻⁸ per operation), compounded by accumulation and subsequent generation. The trial was reverted pending waveform assessment; the bitwise test remains a diagnostic for the exact-order kernel, not a general generated-audio acceptance gate.

The scalar BF16 reference compiles to `FMADDS`, so the second four-row candidate used fused multiply-add for every row while sharing one F32 activation load per column. The strict native bitwise test passes across 11 column widths and 16 seeded matrices per width; released FlowLM/Mimi/one-frame tests and the zero-warm-allocation gate pass. A 25-frame numerical comparison against the separately captured unchanged ARM baseline reports zero affected samples and zero measured error for this candidate. Bitwise kernel parity and matching PCM bytes are observations, not generated-signal hash acceptance gates. Three rotated fresh-process runs (five 25-frame calls each) on the same CIX P1 measured median 1,982,356,342 ns on the previous NEON FMA build versus 1,548,844,666 ns with fused BF16 x4, about 1.28× faster for that workload. First-chunk medians were 314,349,987 versus 222,825,996 ns; five-frame medians 754,998,520 versus 572,237,663 ns. Both paths reported 0 B and 0 allocations per warm call. A three-call fused-BF16 profile sampled 5.12 CPU seconds: `bf16DotF32x4Arm64Asm` was 2.32 seconds flat (45.31%); its share rose even while wall time fell. This remains native ARM64 evidence for the pinned preset voice, not a broader quality or sustained-load claim. The full native SIMD package also triggered an SGEMM parity test that fails identically on the pre-BF16 binary; two source-boundary tests require the repository tree absent from the transfer bundle. Focused BF16/GEMV/FMA native checks passed five repeats. A bounded shared-model concurrency check then used two request-owned sessions, five frames each, with distinct fixed noise streams and three simultaneous generations per test run. Five native CIX P1 test processes passed: each worker emitted 9,600 samples and had zero measured max/RMS drift against its separately run serial counterpart. This checks cross-talk and reset/reuse for these two workers. A SHA-checked source bundle for commit `8e75ec54` was compiled on the CIX P1 with Go 1.26.2 and its local ARM64 C compiler; three native `-race` test processes also passed the two-session check with zero measured serial-versus-concurrent PCM drift and no reported Go race. The host whole-tree race run passed, but skipped the opt-in released test without model files. A follow-up widened this opt-in test to four request-owned sessions and six concurrent five-frame generations per process. Three ordinary and three native `-race` CIX P1 processes passed; each worker emitted 9,600 samples with zero measured max/relative-RMS drift from its serial reference. This bounded check covers four workers and repeated session resets, without measuring throughput. A separate opt-in timing diagnostic warmed the four sessions, then ran three serial trials and three concurrent trials of 20 five-frame requests each on the same board with `GOMAXPROCS=2`. Serial totals were 11.2965–11.3054 s per 20 requests; parallel totals were 5.6302–5.6800 s per 20 requests (about 1.99–2.01× batch throughput, with no cold setup charged). Each request emits 9,600 samples (0.4 s), so even this bounded concurrent case takes about 0.282–0.284 s per request's 0.4 s of audio *at batch throughput*; individual request latency and p95/p99 were not measured, and the host load is uncontrolled. Longer runs, cancellation, latency distribution and sustained-load/production admission remain open.

A later comparison recovered the original ARM baseline PCM from its saved diagnostic binary and verified its 192,000-byte payload against the diagnostic's logged output identity; the saved non-fused trial PCM is also 192,000 bytes. Hashes here serve *historical artifact identification only*, never waveform acceptance. On the CIX P1 deterministic 25-frame-*capacity* run, EOS stops generation after 15 frames (28,800 F32 samples at 24 kHz, 1.2 s). The 48,000-sample caller buffer has 19,200 unwritten zeros. Of the emitted samples, 28,711 differ. The emitted baseline peak is 0.333923668 and RMS is 0.057865876. Absolute error max is 3.13036144×10⁻⁵ (sample 15,290; 9.37448×10⁻⁵ of peak), emitted-sample RMS is 1.73419166×10⁻⁶ (2.99692×10⁻⁵ of signal RMS, 90.47 dB SNR). Absolute-error percentiles over the full 48,000-sample buffer, including the zero tail: p50 4.19×10⁻⁹, p95 1.79×10⁻⁶, p99 6.19×10⁻⁶, p99.9 1.63×10⁻⁵; 173 exceed 1×10⁻⁵ and two exceed 3×10⁻⁵. The same-host released parity test now reads a separately captured raw little-endian F32 baseline from `GO_PHERENCE_POCKETTTS_REFERENCE_PCM`, checks finite values and exact sample count, and reports absolute/RMS/peak-relative drift instead of a PCM SHA gate. Provisional measured-error ceilings of max 4×10⁻⁵ and relative RMS 5×10⁻⁵ leave modest headroom above the trial, not a claim of broader speech quality or an automatic change to the existing independent one-frame 3×10⁻⁵ oracle. Both the fused candidate against baseline (zero drift) and a baseline-versus-saved-trial diagnostic comparison (measured drift above) pass the new numerical gate. Converted 16-bit WAVs and a stereo A/B file (baseline left, trial right) were prepared from the full 48,000-sample buffer, so they include 0.8 s of silence after the 1.2 s utterance. Listening assessment and broader utterance/voice quality are **open**, so the non-fused trial remains unqualified. Reference provenance, model/voice/seed/architecture, and native logs must accompany each invocation; absent reference PCM skips rather than passes this opt-in gate.

The released timing benchmark previously set `Bytes/op` to the requested frame *capacity*. Its rate for the 25-frame case used 192,000 bytes even though EOS emitted 28,800 samples (115,200 F32 bytes). The benchmark now warms once, checks the returned sample count, sets bytes from emitted samples, and checks that each timed call returns the same count. Three later CIX P1 fused-BF16 runs (five calls each) measured 25-frame-capacity timings of 1.512, 1.557 and 1.518 s, with zero B and zero allocations per warm call; reported `MB/s` now uses emitted bytes. These later timings are a separate sample set and do not replace the rotated baseline/candidate comparison above.

A separate opt-in four-worker reuse run exercised 40 consecutive five-frame requests per session (160 requests total) on the CIX P1 with shared immutable weights, `GOMAXPROCS=2` and `nice -n 10`. Every 9,600-sample output matched its worker's serial numerical reference within max 4×10⁻⁵/relative RMS 5×10⁻⁵; no request failed. The ordinary run took 45.46 s total (3.52 requests/s aggregate). Measured per-request latency was p50 1.134 s, p95 1.179 s, p99 1.208 s and max 1.214 s: each request emits 0.4 s of audio, so individual latency remains slower than real time. `HeapAlloc` after forced GC changed from 326,996,448 to 326,997,944 bytes (+1,496 B), including test-harness allocations; this single run does not establish a leak slope or process peak RSS. The same 160-request check passed once under native Go `-race` without a reported race or numerical failure. Race instrumentation raised elapsed time to 93.24 s and p95 to 2.374 s; these instrumented timings are not performance baselines. A second ordinary 160-request run under 100 ms `/proc/<pid>/status` polling passed with elapsed 46.15 s, p95 1.196 s and `VmHWM` high-water mark 453,520 KiB (about 443 MiB) across 478 samples. The process also reported a 1,496-byte post-GC `HeapAlloc` change. `VmHWM` is the kernel's process high-water mark observed while the PID existed; this is a bounded single-process memory observation, not a leak slope or steady-state resource budget. Forty requests per worker is not a days-long soak, cancellation gate, listening assessment or production admission.

A separate bounded cancellation pass adds `Session.GenerateIntoContext` without changing the existing `GenerateInto` caller contract. A non-nil context is checked before reset, at the start of each frame, before each flow decode step, before Mimi decode and before success is returned. Cancellation returns `context.Canceled` and the number of *complete* PCM samples already written; the next generation resets the session. It cannot interrupt a transformer, flow or Mimi kernel already in progress, so no hard cancellation-latency bound follows. The opt-in released five-frame test cancels in the noise callback before the first decode and after one complete frame; three native CIX P1 repetitions passed both partial-output/untouched-tail cases and subsequent session reuse. The existing and context-aware five-frame warm paths each retained zero allocations over ten runs on ARM64, and the Intel released tests passed under Go `-race`. A later opt-in asynchronous diagnostic signalled cancellation from another goroutine after frame one had decoded. Five CIX P1 runs returned `context.Canceled`, one complete frame, and an untouched remaining PCM buffer. The observed signal-to-return delays were 4.82–5.02 ms in this bounded case. The signal is issued during the noise callback before flow work for the next frame; it does **not** demonstrate cancellation in the middle of a running transformer, flow or Mimi kernel. The test logs latency without enforcing a limit. Deadline timing, cancellation during a long kernel and longer-request latency distribution remain open.

To check the context refactor against the unchanged legacy `GenerateInto` path, a later rotated CIX P1 comparison used the pre-context emitted-byte benchmark binary and a binary from `2508c278`, each at `GOMAXPROCS=2`, five warm 25-frame-capacity calls per fresh process. Three pre-context samples were 1.543, 1.551 and 1.542 s/op; three post-context samples were 1.593, 1.546 and 1.544 s/op. Both reported 0 B and 0 allocations per warm call. The sample distributions overlap; this bounded run establishes no clear timing regression or gain, and does not replace sustained-load evidence.

The opt-in reuse test now accepts `GO_PHERENCE_POCKETTTS_REUSE_REQUESTS=1..200` (default 40), bounded to four workers. With 200 requests per worker, a SHA-checked native CIX P1 binary under `GOMAXPROCS=2`, `nice -n 10` completed 800 five-frame requests in 3m53.18s after warm-up (about 3.43 requests/s aggregate). It compared every 9,600-sample output against the corresponding serial reference within the established max/relative-RMS limits and had no failed requests. Per-request latency p50 was 1.168 s, p95 1.206 s, p99 1.220 s, max 1.245 s; emitted audio is 0.4 s/request. Post-GC `HeapAlloc` changed from 327,002,592 to 327,004,088 bytes (+1,496 B). A 200 ms `/proc/<pid>/status` poll saw process `VmHWM` of 453,188 KiB (about 443 MiB) across 1,148 samples. The run lasted under four minutes, and neither it nor the single heap delta establishes a long-term leak slope, hard latency ceiling or production readiness.

A follow-up same-board, multi-utterance numerical comparison ran five fixed prompts through the pinned released model, tokenizer and Alba voice. The pre-BF16 source was `bcfb62b9`; the current fused source was `2fdf579e`. Both ARM64 binaries used the same temporary Go CLI, config and deterministic F32 noise, one LSD step, EOS threshold -4 and 25-frame capacity. Emitted samples were: “Hello world!” 28,800; “A calm breeze crosses the harbor at dawn.” 48,000; “Português é uma língua bonita.” 48,000; “Can you read this aloud?” 36,480; “The train arrives at seven thirty five.” 48,000. Each 48,000-sample F32 caller buffer matched its same-host pre-BF16 counterpart numerically with zero affected samples, max absolute error 0 and relative RMS error 0; no output hashes were used as acceptance gates. The new opt-in `TestReleasedMultiUtteranceNumericalParity`, gated by `GO_PHERENCE_POCKETTTS_REFERENCE_DIR`, passed three native CIX P1 repetitions against the preserved baseline files. The five 24 kHz mono clips were distributed individually as MP3 for listening. User feedback found the fixed-pattern-noise “numbers” clip blank: its source PCM RMS was 0.000269 and peak 0.00854, versus RMS 0.045–0.063 on the other four clips; its WAV mean level was −71.4 dB. Its baseline parity therefore **does not** qualify audible generation. The same prompt with CLI-style seeded Gaussian noise (`seed=0`, temperature 0.3) had first-two-second PCM RMS 0.0745 and intelligible words, but the 25-frame cap cut off the utterance. Raising capacity to 64 and 128 with the same seed returned 32 frames (61,440 samples, 2.56 s) before EOS both times; the first two seconds of PCM stayed unchanged. The pre-BF16 `bcfb62b9` and current source produced the same 64-frame-capacity PCM in a same-host numerical comparison with zero measured drift. A longer 2.56-second individual MP3 was attached, and the user confirmed that this seed-0 “numbers” replacement works. This listening result applies to that one prompt and seed; EOS alone cannot prove completeness elsewhere. The fixed-noise `TestReleasedMultiUtteranceNumericalParity` remains a bounded numerical regression for its documented fixtures, **not** an independent speech-quality, intelligibility or truncation acceptance. The reported blank clip and capped clip are quality failures for the original listening set. Broader prompts, seeds, voices and human listening remain open.
