# Nemotron GPU source-safety audit — 30 September 2026

The source audit found **confirmed PTX/CUDA failure-cleanup defects** and no demonstrated source defect that caused the 02:16:22 UTC GPU bus loss. The failing CLI binary was built from `ede9ea019fad6732962c9dddc49578fc1add9c90`; its failing process selected `-backend vulkan -vulkan-tower`, after a separate PTX process had exited successfully. This narrows the immediate operation, but does not clear PTX, shared driver state, Vulkan, passthrough or physical hardware as possible contributors. The [incident timeline](nemotron-gpu-xid79-investigation-20260930.md) retains the guest/host evidence and missing physical telemetry.

## Confirmed failure-path defect — PTX cleanup (high on a driver fault)

- At **`ede9ea01` and current `d524ee83`**, `model/nemotrondiarization/ptx_tower.go:81-105` calls `ptx.SyncErr()` at line 92, **discards its error**, marks the tower closed, then frees scratch, weights and 30 layer owners. `backends/nvidia/runtime/runtime.go:532-537` reports a failing `cuCtxSynchronize`; `runtime.go:322-339` calls `cuMemFree`, discards its result and sets `Ptr=0` even on failure. A failed sync cannot certify that outstanding work has finished. The close path can therefore attempt release of buffers still referenced by queued GPU work and cannot report/retry a failed free. This is a code-level lifetime/diagnostic defect conditional on sync/free failure. It has **not** been shown to trigger Xid 79; the September 30 failing process was Vulkan.
- The tower's `ForwardRows` deferred cleanup (`ptx_tower.go:140-150`) and standalone layer `ForwardBuffer` (`ptx_layer.go:179-190`) *do* join `SyncErr()` before freeing their transient owners. They still free on a failed sync, so an error/uncertain submission has no fail-closed quarantine at these PTX paths. The PTX stacking projector's `Close` (`stacking_projector_device.go:26-55`) frees buffers without reporting a preceding sync result; its successful projection path synchronises before download (`:151-170`). Error-path coverage requires a separate mock test.
- Severity is **high for error-path integrity**: buffers may be released or marked gone after CUDA has lost the ability to prove completion. This is not evidence of an ordinary-path out-of-bounds shader access. Do not change API semantics by silently skipping cleanup or treating `cuMemFree` as a recovery operation. A fix needs an error-returning checked free, a terminal/uncertain context state, retained owners on failed sync/free, explicit process-level recovery policy and tests for repeated close. Keep the current GPU hold in place while that is designed.

## Vulkan failure-path and bounds review

- `backends/vulkan/vulkan_dispatch.go:564-580` resets the fence, submits, retains `vkPending`, and waits. A failed submission is marked uncertain. `vulkan_lifetime.go:153-206` treats a non-timeout fence error as uncertain; `VK_ERROR_DEVICE_LOST` also latches `vkLost`. `vulkan_plan.go:267-333` preflights every stage, serially records barriers and submissions, and does not submit a cancelled partial recording. Its `Close` (`:336-365`) refuses to destroy an in-flight plan. `vulkan_arena.go:101-119,183-208` and `vulkan_buf.go:185-317` reject access or checked frees while pending/quarantined. `model/nemotrondiarization/vulkan_streaming_tower.go:28-66` retains an owner after failed close. These guards explain the observed `Vulkan submission still in flight` and cleanup error **after** device loss; no subsequent submit/free was found on that path.
- `vulkan_barrier.go:22-65` records host-write→compute, compute→compute and compute→host barriers; a successful fence is still required for host access. `vulkan_plan.go:55-99,192-254,267-333` copies stage metadata, preflights replacement bindings before rebind, and retains referenced buffers through a pending submission. `vulkan_dispatch.go:442-501` checks descriptor range/alignment, buffer ownership and dispatch/device limits. Arena offsets/capacity have checked arithmetic (`vulkan_arena.go:58-101`); `VkAttentionF32.Stage` checks width, heads, sequences, output aliasing and exact bound range (`vulkan_attention.go:48-93`). The attention GLSL uses guarded query/key/channel loads and barriers reached by all lanes (`shaders/attention_f32.glsl:1-101`). Source inspection found no concrete out-of-range access in the reviewed 541-row maximum-prefix tower path.
- This is a **bounded review**, not a proof for all compiled SPIR-V and drivers. Shader/host push-layout parity, every operation in the 14-stage layer plan, descriptor writes under real validation layers, and a repeated long-request soak remain GPU-unverified. A fence returning `-4` at tower layer 29 locates **observation**; the originating command could be earlier or outside this process. The application log lacks subsecond timestamps to order it against the guest Xid 79.

## CUDA bounds/synchronisation scope and prior fixes

- `model/nemotrondiarization/ptx_layer.go:170-265` checks positive bounded rows, input/output sizes and overlap; scratch capacity is validated at `ptx_layer_scratch.go:16-60`. The released tower limits rows to `maxPreparedDiarizationRows=541`. `backends/nvidia/runtime/sgemm.go:30-75`, `whisper_bounds.go:11-43`, and `rope_attention.go` validate buffer extents and shapes before the reviewed projection/attention/RoPE launches. Host checks do not prove PTX assembly safe for every shape or that a pre-fault asynchronous error would be attributed to its initiating launch.
- The previously fixed CUDA context boundary is still present in the **failing revision**: `backends/nvidia/runtime/driver_scope.go:7-13` pins the OS thread and holds `cudaMu` through context selection and driver calls; `runtime.go:505-537,620-670` uses the same scope for sync and kernel launch. The model-free `context_boundary_test.go` and `driver_scope_test.go` exercise thread/lock identity and concurrent calls. These tests do not cover all library entry points, injected failed sync/free in the PTX tower, or a real CUDA/Vulkan interaction. Prior Xid79 incidents on driver 580 with different CUDA workloads rule out a Nemotron-only or driver-610-only *explanation*, but do not rule out multiple defects or a common card/passthrough fault.
- Comparing `ede9ea01..d524ee83` shows **no changes** to `backends/vulkan`, `backends/nvidia/runtime`, `model/nemotrondiarization/ptx_tower.go`, `vulkan_tower.go`, `vulkan_layer.go`, `stacking_projector_device.go` or the CLI dispatch. Later CPU-only buffer reuse cannot be blamed for the saved failing binary.

## CPU-only gates and missing evidence

`GO_PHERENCE_DISABLE_NVIDIA=1` focused offline Vulkan lifetime, barrier, plan, arena, limits and shader-layout tests and fake-driver CUDA context/stream/module tests passed. The model-free Nemotron PTX malformed/selection/context tests passed. Logs are under `/workspace/tmp/nemotron-gpu-source-audit-{vulkan,cuda,model}-tests.log`. These mock/static tests verify rejection and ownership rules represented in the harness; none executes the damaged GPU. They do **not** inject a failed `cuCtxSynchronize` into tower Close or validate a native shader. The confirmed PTX cleanup paths are therefore source-proven with a test gap, not a tested Xid reproducer.

Falsification and next tests (only after separately approved recovery):

1. **PTX cleanup hypothesis:** CPU fake-driver test injects sync failure with queued work, asserts tower/projector retain all owners, report the error and never call `cuMemFree`; injects free failure and checks pointer remains retryable. If that cannot be demonstrated in the failing binary's error path, revise the finding. It would still not establish bus-loss causation.
2. **Vulkan shader/plan hypothesis:** CPU mocks inject failure at each recorded stage and cancellation boundary, assert no freed/rebound resources before fence confirmation. After recovery, isolate tiny single-plan runs with Vulkan validation and explicit per-stage completion in a separate process. A reproducible validation error on that path would support a software trigger; repeated clean bounded runs alone would not disprove an intermittent bug.
3. **Shared card/link/driver hypothesis:** run an independent third-party GPU baseline before our code, with continuous physical-host PCIe AER/link, guest Xid and GPU power/temperature/clock telemetry, bounded duration and fail-closed stop on the first device-query or driver error. A recurrent Xid79 under independent code with physical link/rail evidence would shift weight toward hardware/platform; absence of logged AER or an online UPS cannot falsify it. Then compare isolated PTX and Vulkan tiny workloads in separate processes, escalating shapes only on stable baseline. Compute Sanitizer and Vulkan validation are diagnostic workloads, not timing samples. None is authorised now.

Physical GPU/root-port link counters, local PSU rail and at-fault telemetry, a decoded NVIDIA crash dump and a stable recovered device are missing. Rui authorised source/CPU-only investigation, **not** GPU execution, reset, driver reload, service restart or reboot. @default owns host recovery coordination.
